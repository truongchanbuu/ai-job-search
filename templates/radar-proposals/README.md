# Minimal, profile-grounded Upwork proposals

These are editing patterns, not copy-and-paste applications. Their runtime
briefs live in `config/radar.example.yaml` → private `radar.yaml` or approved DB
configuration. Job Details **T** selects a brief, **G** explicitly generates a
draft after evaluation approval. No automatic submission occurs.

| Pattern | Use |
|---|---|
| [Problem first](problem-first.md) | A clear, bounded technical deliverable |
| [Focused repair](focused-repair.md) | A reported bug/regression |
| [Integration](integration.md) | API, webhook or data flow |
| [Salesforce change](salesforce-change.md) | A verified Salesforce skill match |
| [Clarify scope](clarify-scope.md) | A plausible job with missing requirements |

Replace each slot using the actual job and approved profile. A proof slot must be
one relevant **verified + shareable** fact, with its real experience context.
Omit an optional public link if none is approved. Never send unresolved slots.
If there is no relevant evidence, update/review the profile or choose a different
opportunity; never substitute a fabricated client, qualification or achievement.

Aim for compact paragraphs, no padded minimum length. Default runtime ceilings
are editorial limits, not scientifically optimal lengths. One useful closing
question is usually enough; remove questions already answered in the posting.
Client-requested information/screening answers still takes priority and is handled
separately. A technology keyword match only suggests relevance; inspect the actual
work before claiming fit. See [research and implementation](../../docs/radar/plan/proposal-templates.md).
